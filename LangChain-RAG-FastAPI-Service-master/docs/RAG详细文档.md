## 一、整体流程总览

### 是什么

RAG（Retrieval-Augmented Generation）= 检索增强生成。核心思想：**先从知识库中检索相关文档，再把文档交给 LLM 生成回答**，而不是让 LLM 凭空回答。

### 为什么

纯 LLM 有两个致命问题：
1. **知识截止**：LLM 的训练数据有截止日期，无法回答关于最新内容的问题
2. **幻觉**：LLM 会编造看似合理但错误的内容

RAG 通过"先检索、后生成"，让 LLM 基于真实文档回答，大幅降低幻觉率。

### 本项目的 RAG 流程

```
用户问题
   │
   ▼
┌──────────────────────────────────────────────────────┐
│ 第一步：HyDE 查询优化                                  │
│ LLM 根据问题生成假设性回答，用回答去做检索（而非问题本身）  │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 第二步：多 Query 扩展                                  │
│ LLM 将问题改写为 3 个语义等价但表述不同的版本             │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 第三步：多路混合检索                                    │
│ 每个查询版本分别执行：向量检索 + BM25 检索               │
│ HyDE 文档额外执行：向量检索 + BM25 检索                 │
│ 知识库和笔记分开检索，互不干扰                           │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 第四步：RRF 融合排序                                   │
│ 所有路的检索结果用 Reciprocal Rank Fusion 合并去重       │
│ 知识库取 Top 5，笔记取 Top 3                           │
└──────────────────────┬───────────────────────────────┘
                       ▼
┌──────────────────────────────────────────────────────┐
│ 第五步：MapReduce 并发摘要                              │
│ Map：每篇文档并发调 LLM 生成单篇摘要                    │
│ Reduce：所有摘要交给 LLM 二次融合，生成最终回答          │
└──────────────────────────────────────────────────────┘
```

## 二、文档处理与存储

### 2.1 文档上传与解析

#### 是什么

用户上传文档（txt/pdf/md/pptx/docx）后，系统自动解析、切片、向量化、存入检索系统。

#### 为什么

LLM 的上下文窗口有限（几千到几万 token），不能把整个文档塞进去。需要把文档切成小块（chunk），只检索最相关的几块交给 LLM。

#### 怎么做

**文件路径**：`DocumentProcessor.java`

```
文件上传
   │
   ▼
Apache Tika 解析（统一处理 txt/pdf/md/pptx/docx）
   │
   ▼
MD5 去重检查 ──→ 已存在且向量数据完好 → 跳过
   │              已存在但向量数据丢失 → 清理旧记录，重新处理
   ▼
中文感知切片（按标点层级切分，chunkSize=200，overlap=20）
   │
   ▼
每个切片 → 向量化（Embedding）→ 存入 ChromaDB + BM25 索引
```

#### 切片策略详解

**问题**：英文 RAG 常用的 `RecursiveCharacterTextSplitter` 按空格/换行切分，对中文效果很差——会把一个句子从中间切断，破坏语义完整性。

**解决**：按中文标点层级切分：

```
优先级：\n\n → \n → 。 → ！ → ？ → . → ! → ? → ； → ; → ， → ,
```

先尝试用 `\n\n`（段落）分割，如果只产生一段，降级到 `\n`，依次降级直到找到能产生多段的分隔符。

**为什么需要 overlap（重叠）**：

```
chunk1: "...机器学习是人工智能的一个子集，它通过"
chunk2: "它通过数据训练模型来做出预测..."
        ^^^^^^^^ 重叠部分 ^^^^^^^^
```

没有 overlap，"它通过"这个指代关系就断了。检索到 chunk2 时 LLM 不知道"它"指什么。

#### MD5 去重

**问题**：用户重复上传同一文件，导致向量库中出现大量重复切片，浪费存储且污染检索结果。

**解决**：上传前计算文件 MD5，跳过已存在的文档。双重校验：MD5 记录存在 **且** 向量数据存在才跳过，防止重启后向量数据丢失但 MD5 记录还在的边界情况。

### 2.2 双路存储

#### 是什么

每个文档同时存入两个系统：
- **ChromaDB**：向量数据库，支持语义相似度检索
- **Lucene BM25**：内存倒排索引，支持关键词检索

#### 为什么

| 检索方式 | 擅长 | 不擅长 |
|---------|------|-------|
| 向量检索 | 语义匹配（"怎么提升记忆力" → "艾宾浩斯遗忘曲线"） | 精确关键词（搜"JVM GC"可能匹配到不相关的"Java性能优化"） |
| BM25 | 关键词匹配（词频+逆文档频率） | 语义理解（搜"怎么记住东西"匹配不到"间隔重复"） |

单一检索方式有盲区，双路检索取长补短。

#### 怎么做

**向量存储**（`VectorStoreService.java`）：
- 优先连接 ChromaDB（持久化），连接失败降级为 `ConcurrentHashMap`（内存）
- 用户隔离：检索时加 `filter: user_id = xxx`

**BM25 存储**（`Bm25Service.java`）：
- 基于 Lucene，每个用户独立的内存索引（`ByteBuffersDirectory`）
- 使用 `StandardAnalyzer`（支持中英文分词）
- 查询时自动转义特殊字符，防止 Lucene 查询语法注入

## 三、HyDE 查询优化

### 是什么

HyDE = Hypothetical Document Embedding（假设性文档嵌入）。先让 LLM 根据问题生成一个"假设性回答"，再用这个回答去做向量检索。

### 为什么

**核心问题**：用户的查询通常很短（10-20字），而文档是长文本（几百字）。短查询和长文档在向量空间中的表示距离较远，直接检索效果不好。

**示例**：
```
用户查询（12字）: "什么是遗忘曲线"
文档（200字）: "艾宾浩斯遗忘曲线是德国心理学家赫尔曼·艾宾浩斯在1885年
              发表的著作《记忆》中提出的理论。该理论描述了人类记忆
              随时间推移而衰减的规律。研究表明，在学习后的20分钟内
              会遗忘约42%的内容，1天后遗忘约74%，6天后遗忘约75%..."
```

短查询的向量表示语义密度低，跟长文档的向量距离远。

### 怎么做

**文件路径**：`RagService.java`

```java
// HyDE Prompt
"基于以下问题，生成一个详细的假设性回答，我会根据你的这个假设性回答在向量数据库里检索文档：

问题：{query}

假设性回答："
```

**流程**：
```
原始查询: "什么是遗忘曲线"（12字）
    │
    ▼ LLM 生成假设性文档
假设性文档: "遗忘曲线是德国心理学家艾宾浩斯提出的理论，
           描述了人类记忆随时间衰减的规律。研究表明，
           学习后20分钟遗忘42%，1天后遗忘74%..."（100+字）
    │
    ▼ 用假设性文档做向量检索
检索结果: [实际的遗忘曲线笔记] ← 语义匹配度更高
```

**为什么有效**：向量模型对长文本的语义编码比短问题更准确。假设性文档虽然可能有幻觉，但它与真实文档在**语义空间**中更接近。

**兜底策略**：
```java
try {
    Response<AiMessage> response = chatModel.generate(UserMessage.from(prompt));
    return response.content().text();
} catch (Exception e) {
    log.warn("HyDE generation failed, using raw query: {}", e.getMessage());
    return query;  // 失败时退化为原始查询
}
```

LLM API 可能超时、限流、网络异常。HyDE 是锦上添花，不是必须的。失败时用原始查询继续检索，保证系统可用性。

### HyDE 的局限性

| 局限 | 说明 |
|------|------|
| 增加延迟 | 需要额外调一次 LLM，增加 2-5 秒 |
| 可能引入噪声 | 假设性文档的幻觉可能跟真实文档不一致 |
| 不适合精确查询 | "我的笔记ID是123" 这种精确查询不需要 HyDE |

本项目用 HyDE 生成假设性文档，同时保留原始查询用于 Multi-Query 扩展，两者互补。

## 四、多 Query 扩展

### 是什么

将用户的一个问题用 LLM 改写成 3 个语义等价但表述不同的版本，加上原始查询共 4 个版本，分别执行检索。

### 为什么

**核心问题**：同一个意思，用户可能用一种说法，笔记/文档用另一种说法。单一查询可能漏掉语义相同但措辞不同的文档。

**示例**：
```
用户查询: "怎么提升记忆力"
笔记标题: "记忆增强的五种方法"
知识库文档: "提高记忆效率的科学技巧"
```

直接搜"怎么提升记忆力"，可能匹配不到上面两个文档。但如果同时搜 4 个版本，命中率大幅提升。

### 怎么做

**文件路径**：`QueryExpander.java`

```java
// 扩展 Prompt
"请将以下查询改写为3个不同的版本，保持语义相同但使用不同的表述方式。
要求：
1. 每个版本一行，不要编号
2. 使用不同的关键词和句式
3. 可以包含同义词、缩写、全称等不同表达
4. 只返回改写结果，不要有其他文字
5. 每个版本不超过20个字

原始查询：{query}

改写结果："
```

**流程**：
```
原始查询: "怎么提升记忆力"
    │
    ▼ LLM 改写
    ├── "记忆增强的方法有哪些"
    ├── "提高记忆效率的技巧"
    └── "如何改善记忆能力"
    │
    ▼ 4 个查询分别执行检索
```

**后处理**：
- 去掉编号前缀（`1.`、`-`、`*`）
- 去掉引号
- 限制每个变体不超过 50 字
- 去重（跟原始查询相同则跳过）
- 最多保留 3 个扩展（不含原始查询）

**兜底策略**：LLM 调用失败时，仅使用原始查询，不中断检索流程。

### HyDE vs Multi-Query 区别

| | HyDE | Multi-Query |
|--|------|-------------|
| 变换方向 | 问题 → 答案 | 问题 → 问题 |
| 变的是什么 | 文本类型（问句→陈述句） | 表述方式（同义改写） |
| 生成数量 | 1 个 | 3 个 |
| 解决什么 | 短查询与长文档向量不匹配 | 用词不同导致的漏检 |
| 对检索的贡献 | 语义深度 | 覆盖面 |

两者互补：HyDE 补语义深度，Multi-Query 补覆盖面。

## 五、双路检索：向量 + BM25

### 5.1 向量检索

#### 是什么

将文本通过 Embedding 模型转换为高维向量，在向量空间中计算余弦相似度，返回最相似的文档。

#### 为什么

向量检索能理解语义：
- 查询："怎么记住东西"
- 文档："间隔重复是一种记忆方法"
- 词完全不同，但语义相近 → 向量距离近 → 能匹配上

#### 怎么做

**文件路径**：`VectorStoreService.java`

```
查询文本 → Embedding 模型（智谱 embedding-3）→ 查询向量
    │
    ▼
ChromaDB 向量检索（带 user_id 过滤）→ Top K 结果
```

**用户隔离**：
```java
Filter filter = new IsEqualTo("user_id", userId);
EmbeddingSearchRequest request = EmbeddingSearchRequest.builder()
        .queryEmbedding(queryEmbedding)
        .maxResults(topK)
        .filter(filter)
        .build();
```

确保 A 用户搜不到 B 用户的笔记和知识库。

### 5.2 BM25 检索

#### 是什么

BM25（Best Matching 25）是经典的关键词检索算法，基于词频（TF）和逆文档频率（IDF）评分。

#### 为什么

BM25 能精确匹配关键词：
- 查询："JVM GC"
- 文档："JVM 垃圾回收机制详解"
- 关键词精确命中 → BM25 高分

向量检索可能把"JVM GC"匹配到不相关的"Java性能优化"，BM25 不会。

#### 怎么做

**文件路径**：`Bm25Service.java`

```
查询文本 → Lucene QueryParser 解析 → BM25 搜索 → Top K 结果
```

**每个用户独立索引**：
```java
private final Map<String, Directory> userIndexes = new ConcurrentHashMap<>();
```

每个用户有自己的内存索引，互不干扰。

**特殊字符转义**：
```java
String escapedQuery = QueryParser.escape(query);
```

防止用户输入的特殊字符（`+`、`-`、`&&` 等）被当作 Lucene 查询语法解析。

### 5.3 知识库和笔记分开检索

**问题**：知识库和笔记是两种不同性质的数据。笔记是用户自己写的，跟用户意图更相关；知识库是外部上传的文档。

**解决**：分开检索，分开融合，最后合并时笔记优先。

```
知识库检索 → Top 5（独立 RRF 融合）
笔记检索 → Top 3（独立 RRF 融合）
    │
    ▼
合并：笔记在前 + 知识库在后
```

## 六、RRF 融合排序

### 是什么

RRF（Reciprocal Rank Fusion）= 逆排名融合。一种将多路检索结果合并排序的算法。

### 为什么

多路检索（4个查询 × 2种检索 + HyDE × 2种检索 = 10路）会产生大量结果，很多文档在多路中重复出现。需要一种算法：
1. 去重（同一文档只保留一份）
2. 排序（在多路中都排名靠前的文档应该排在前面）

简单的"取交集"太严格（可能漏掉好文档），"求平均分"对不同检索方式的分数不可比。RRF 只看排名，不看分数，天然适合融合不同来源的排名列表。

### 怎么做

**文件路径**：`HybridRetriever.java`

**RRF 公式**：
```
score(d) = Σ 1/(k + rank_i(d))

其中：
- d = 文档
- k = 常数 60（经验值，避免排名靠前的文档分数过高）
- rank_i(d) = 文档 d 在第 i 路检索结果中的排名（从 1 开始）
- Σ = 对所有路的分数求和
```

**示例**：

```
文档A 在 查询1向量 排名第3   → 1/(60+3) = 0.01587
文档A 在 查询2BM25 排名第5  → 1/(60+5) = 0.01538
文档A 在 HyDE向量 排名第1   → 1/(60+1) = 0.01639
                              ─────────────────────
文档A 最终 RRF 分数          = 0.04764

文档B 在 查询1向量 排名第1   → 1/(60+1) = 0.01639
文档B 在其他路都没出现        → 0
                              ─────────────────────
文档B 最终 RRF 分数          = 0.01639
```

文档A 在 3 路中都出现且排名不错，分数比只在 1 路排名第 1 的文档B 更高。

**实现细节**：

```java
private List<Map<String, Object>> rrfFusion(List<List<Map<String, Object>>> allRankings, int topK) {
    Map<String, Double> rrfScores = new HashMap<>();      // RRF 分数累加器
    Map<String, Map<String, Object>> docCache = new HashMap<>();  // 文档内容缓存

    for (List<Map<String, Object>> ranking : allRankings) {
        for (int rank = 0; rank < ranking.size(); rank++) {
            Map<String, Object> doc = ranking.get(rank);
            String docKey = getDocKey(doc);

            // RRF 分数累加: 1/(k + rank)，rank 从 1 开始
            double rrfScore = 1.0 / (RRF_K + rank + 1);
            rrfScores.merge(docKey, rrfScore, Double::sum);  // 同一文档累加分数

            docCache.putIfAbsent(docKey, doc);  // 缓存文档内容
        }
    }

    // 按 RRF 分数降序排序，取 top-K
    return rrfScores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topK)
            .map(entry -> docCache.get(entry.getKey()))
            .collect(Collectors.toList());
}
```

**文档去重标识**（`getDocKey`）：
- 知识库切片：用 `chunk_id`（格式：`md5_索引`）
- 笔记：用 `note_id`
- 兜底：用 `content` 的 hashCode

### 为什么每路查 topK × 2

```java
vectorStoreService.searchKnowledge(userId, q, topK * 2);  // 查 10 个
```

每路多查一倍是为了给 RRF 融合留余量。如果每路只查 5 个，融合后可能漏掉在某一路排名第 6 但在其他路排名靠前的文档。多查一些，让 RRF 有更多候选文档可以交叉排序。

### 完整检索路径图（知识库为例，topK=5）

```
查询1 ──┬── 向量检索 → 10 个结果
        └── BM25 检索 → 10 个结果
查询2 ──┬── 向量检索 → 10 个结果
        └── BM25 检索 → 10 个结果
查询3 ──┬── 向量检索 → 10 个结果
        └── BM25 检索 → 10 个结果
查询4 ──┬── 向量检索 → 10 个结果
        └── BM25 检索 → 10 个结果
HyDE ──┬── 向量检索 → 10 个结果
       └── BM25 检索 → 10 个结果
                          │
                          ▼ 100 个结果（大量重复）
                    RRF 融合去重排序
                          │
                          ▼
                    最终 5 个结果
```

笔记检索同理，topK=3，每路 6 个，最终 3 个。

## 七、MapReduce 并发摘要

### 是什么

检索到文档后，不是把所有文档直接扔给 LLM，而是：
1. **Map 阶段**：每篇文档并发调 LLM 生成单篇摘要
2. **Reduce 阶段**：所有摘要交给 LLM 二次融合，生成最终回答

### 为什么

**问题1：串行摘要太慢**

如果串行调用 LLM 总结 3 篇文档，每篇需要 3-5 秒，总共需要 9-15 秒。用户体验极差。

**解决方案**：`CompletableFuture.supplyAsync` 线程池并发执行

```
串行：文档1(3s) → 文档2(5s) → 文档3(4s) = 12秒
并发：文档1(3s) ─┐
      文档2(5s) ─┤ 并行 = 5秒（取最慢的）
      文档3(4s) ─┘
```

**问题2：多文档直接融合质量差**

3 篇文档的原始内容可能很长、有重复、有矛盾。直接让 LLM 处理大量原始文本：
- Token 消耗大
- LLM 容易遗漏关键信息
- 回答质量不稳定

**解决方案**：先压缩（Map），再融合（Reduce）

```
文档1(1000字) → 摘要1(100字) ─┐
文档2(800字)  → 摘要2(100字) ─┤→ 二次融合 → 最终回答
文档3(1200字) → 摘要3(100字) ─┘
```

### 怎么做

**文件路径**：`RagService.java`

#### Map 阶段 — 并发单文档摘要

```java
List<CompletableFuture<String>> summaryFutures = topDocs.stream()
    .map(doc -> CompletableFuture.supplyAsync(() -> {
        // 构造单文档摘要 Prompt
        String prompt = "基于以下问题和文档内容，生成简洁的摘要：\n\n"
                      + "问题：" + query + "\n\n文档：\n" + doc + "\n\n摘要：";
        Response<AiMessage> response = chatModel.generate(UserMessage.from(prompt));
        return response.content().text();
    }, taskExecutor)           // 使用自定义线程池
    .orTimeout(30, TimeUnit.SECONDS))  // 30秒硬超时
    .collect(Collectors.toList());
```

**关键设计点**：

**1. 自定义线程池**（`AsyncConfig.java`）：
```java
executor.setCorePoolSize(4);      // 核心线程：常驻
executor.setMaxPoolSize(16);      // 最大线程：突发负载时扩容
executor.setQueueCapacity(100);   // 队列：超出核心线程的任务排队
executor.setThreadNamePrefix("async-");  // 线程名前缀：方便排查问题
```

不用 `ForkJoinPool.commonPool()`，避免阻塞其他异步任务。

**2. 30秒硬超时**：
```java
.orTimeout(30, TimeUnit.SECONDS)
```

LLM API 可能卡住（网络抖动、服务端排队）。超时后 `CompletableFuture` 自动完成（抛出 `TimeoutException`），防止线程永久阻塞。

**3. 降级策略**：
```java
} catch (Exception e) {
    log.warn("Document summarization failed: {}", e.getMessage());
    return doc.substring(0, Math.min(200, doc.length()));  // 截取前200字
}
```

LLM 调用失败时，直接截取原文前 200 字作为"摘要"。粗暴但有效——至少有内容返回给用户。

**4. 结果收集**：
```java
List<String> summaries = summaryFutures.stream()
    .map(f -> {
        try {
            return f.join();  // 阻塞等待结果
        } catch (Exception e) {
            return "摘要生成失败";  // 超时或异常返回默认话术
        }
    })
    .collect(Collectors.toList());
```

#### Reduce 阶段 — 二次融合

```java
if (summaries.size() > 1) {
    // 用分隔符拼接多篇摘要
    String combinedContext = String.join("\n\n---\n\n", summaries);
    // 构造融合 Prompt
    String mergePrompt = "基于以下多个文档的摘要，生成一个综合性的回答：\n\n"
                       + "问题：" + query + "\n\n文档摘要：\n" + combinedContext
                       + "\n\n综合回答：";
    // 调用 LLM 融合
    Response<AiMessage> response = chatModel.generate(UserMessage.from(mergePrompt));
    finalSummary = response.content().text();
} else {
    finalSummary = summaries.get(0);  // 只有一篇，直接返回
}
```

**为什么需要二次融合**：
- 3 篇文档的摘要可能有重复、矛盾、或缺乏连贯性
- 二次融合让 LLM 去重、整合、生成流畅的综合回答
- 这就是 MapReduce 的 Reduce 思想：先分散处理，再汇聚结果

**融合失败的兜底**：
```java
} catch (Exception e) {
    finalSummary = String.join("\n\n", summaries);  // 直接拼接
}
```

#### 来源标注

Map 阶段之前，给每个文档打上来源标签：

```java
String tag = "note".equals(sourceType)
        ? "[来源：笔记《" + title + "》]"
        : "[来源：知识库《" + title + "》]";
return tag + "\n" + content;
```

**为什么需要来源标注**：
1. 让 LLM 回答时可以引用来源（"根据你的笔记..."）
2. 让用户知道答案来自哪里，增加可信度
3. 区分"我写的笔记"和"我上传的文档"，信息权重不同

## 附录：各环节的兜底策略汇总

| 环节 | 可能的故障 | 兜底方案 |
|------|-----------|---------|
| HyDE 生成 | LLM API 超时/限流 | 退化为原始查询 |
| Query 扩展 | LLM API 失败 | 仅使用原始查询 |
| 向量检索 | ChromaDB 连接失败 | 降级为内存向量存储 |
| BM25 检索 | Lucene 异常 | 返回空列表，不阻断流程 |
| 单文档摘要 | LLM 调用失败 | 截取原文前 200 字 |
| 单文档摘要 | 30 秒超时 | `CompletableFuture.orTimeout` 自动中断 |
| 二次融合 | LLM 调用失败 | 直接拼接所有单篇摘要 |
| 整个检索 | 没搜到任何文档 | 返回"未找到相关文档" |
