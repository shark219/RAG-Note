### 2.1 多Query扩展

**文件**: `rag/QueryExpander.java`

**解决什么问题**：用户用A说法提问，知识库用B说法存储。单一查询可能因为措辞不同而漏检。

```
用户查询: "怎么提升记忆力"
知识库有: "记忆增强的五种方法"、"提高记忆效率的科学技巧"
→ 直接搜"怎么提升记忆力"可能匹配不到上面两个文档
```

**怎么做**：

1. LLM收到原始查询，改写为3个语义等价但表述不同的版本
2. 原始查询始终保留，最终得到 1+3=4 个查询
3. 每个查询独立走完整检索链路

```
原始查询: "怎么提升记忆力"
    │ LLM改写
    ├── "记忆增强的方法有哪些"
    ├── "提高记忆效率的技巧"
    └── "如何改善记忆能力"
```

**Prompt设计** (`QueryExpander.java:26-47`):

```
你是一个专业的RAG检索优化助手。请针对用户查询生成3个用于知识库检索的扩展查询。

要求：
1. 保留原始查询的核心意图，不改变问题方向
2. 从不同检索角度扩展：同义词、专业术语、相关概念、文档常见表达
3. 每个查询必须能够独立用于搜索知识库
4. 不要生成答案，不要解释原因
5. 避免简单重复原查询或罗列大量关键词
6. 每个查询长度控制在10~30个字
7. 只输出查询列表，每行一个，不要编号
```

**后处理** (`QueryExpander.java:106-116`):
- 去掉编号前缀 (`1.`、`-`、`*`)
- 去掉引号
- 每个变体不超过50字
- 去重（与原始查询相同则跳过）
- 最多保留3个扩展（不含原始查询）

**兜底**: LLM调用失败时仅使用原始查询，不中断检索流程。

**Token消耗追踪**: 每次扩展记录 `lastExpansionTokens`，写入 `RagTrace`，支持成本核算。

### 2.2 双路检索：向量 + BM25

**为什么需要双路**：

| 检索方式 | 擅长 | 不擅长 |
|---------|------|-------|
| 向量检索 (ChromaDB) | 语义匹配："怎么记住东西" → "间隔重复记忆法" | 精确关键词："JVM GC" 可能误匹配"Java性能优化" |
| BM25 (Lucene) | 关键词精确匹配：词频+逆文档频率 | 语义理解：搜"记东西的方法"匹配不到"间隔重复" |

单一检索有盲区，双路互补。

#### 向量检索

**文件**: `rag/VectorStoreService.java`

```
查询文本 → Embedding模型(智谱embedding-3) → 查询向量
    │
    ▼
ChromaDB 向量检索（cosine相似度，user_id过滤）→ Top K 结果
```

- 优先 ChromaDB（持久化），连接失败降级为 `ConcurrentHashMap`（内存）
- 用户隔离：检索时强制 `filter: user_id = xxx`
- 异步写入：ChromaDB 写入走 `DocumentTaskExecutor` 线程池，不阻塞事务

#### BM25 检索

**文件**: `rag/Bm25Service.java`

```
查询文本 → Lucene QueryParser 解析 → BM25 搜索 → Top K 结果
```

- 基于 Apache Lucene，每个用户独立 `FSDirectory` 磁盘索引 (`data/bm25_index/`)
- `StandardAnalyzer` 分词（支持中英文）
- 查询时自动 `QueryParser.escape()` 转义特殊字符，防止 Lucene 查询语法注入
- 元数据缓存：内存 `ConcurrentHashMap` 存储 doc metadata，避免每次读磁盘

**每路取 topK × 2**: 给 RRF 融合留余量。如果每路只取 topK，融合后可能漏掉在某一路排名靠后但其他路排名靠前的文档。

### 2.3 RRF融合排序

**文件**: `rag/HybridRetriever.java:223-246`

**解决什么问题**：多路检索（4个查询 × 2种检索 = 最多8路）产生大量结果，许多文档在多路中重复出现。需要去重 + 排序。向量检索分数和BM25分数不可直接比较，RRF只看排名不看分数，天然适合融合不同来源。

**RRF公式**:

```
score(d) = Σ 1/(k + rank_i(d))

k = 常数（默认30），rank 从0开始
```

**计算示例**:

```
文档A 在 查询1向量 排名第3   → 1/(30+3) = 0.03030
文档A 在 查询2BM25 排名第5   → 1/(30+5) = 0.02857
文档A 在 查询3向量 排名第1   → 1/(30+1) = 0.03226
                                   ─────────────
文档A 最终 RRF 分数            = 0.09113

文档B 只在 查询1向量 排名第1  → 1/(30+1) = 0.03226
```

文档A在3路中出现排名都不错，分数高于只在1路排第1的文档B。这就是RRF的核心逻辑：**多路共识 > 单路高分**。

**实现** (`HybridRetriever.java:223-246`):

```java
private List<Map<String, Object>> rrfFusion(
        List<List<Map<String, Object>>> allRankings, int topK, int rrfK) {
    Map<String, Double> rrfScores = new HashMap<>();
    Map<String, Map<String, Object>> docCache = new HashMap<>();

    for (List<Map<String, Object>> ranking : allRankings) {
        for (int rank = 0; rank < ranking.size(); rank++) {
            String docKey = getDocKey(doc);
            double rrfScore = 1.0 / (rrfK + rank + 1);  // rank+1 使排名从1开始
            rrfScores.merge(docKey, rrfScore, Double::sum);  // 同一文档累加
            docCache.putIfAbsent(docKey, doc);
        }
    }

    return rrfScores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topK)
            .map(entry -> {
                Map<String, Object> doc = new HashMap<>(docCache.get(entry.getKey()));
                doc.put("rrf_score", entry.getValue());
                return doc;
            })
            .collect(Collectors.toList());
}
```

**文档去重标识** (`getDocKey`, 行267-272):
- 知识库切片：`chunk_id`（格式：`md5_索引`）
- 笔记：`note_id`
- 兜底：`content.hashCode()`

**消融支持**: `rrfK` 可通过 `AblationConfig` 调整（参数实验 R-7a~d: k=10/30/60/100）。

### 2.4 Rerank精排

**文件**: `rag/RerankerService.java`

**解决什么问题**：RRF融合只看排名，不知道文档内容和查询的语义匹配度。排名靠前但内容不相关的文档需要被过滤。Cross-Encoder 将查询和文档拼接后过Transformer，能精确判断相关性——但速度慢，所以只对融合后的Top K候选做精排。

**流程**:

```
RRF融合后的Top K候选 (约10条)
    │
    ▼
POST {baseUrl}/rerank (智谱AI rerank API)
  body: { model, query, documents[], top_n, return_documents: false }
    │
    ▼
按 relevance_score 降序重排
    │
    ▼
动态Top-N过滤 (dynamicTopN):
  ├─ score > 0.7  → 全部保留（高质量）
  ├─ 0.5 ≤ score ≤ 0.7 → 最多保留2条（中等质量）
  └─ score < 0.5  → 丢弃
```

**动态Top-N策略** (`RerankerService.java:95-117`): 不是固定取Top K，而是按分数阈值过滤。高置信度的全保留，边缘质量的限量保留，低质量的直接丢弃。这样做的好处是：当检索结果普遍质量不高时不会强行凑数。

**兜底**: API调用失败时返回原始排序结果，不阻断检索流程。

**配置** (`application.yml`): `enabled: false` — 默认关闭，需要配置API Key后手动开启。

### 2.5 流水线编排

**文件**: `rag/HybridRetriever.java`

**知识库检索** (`searchKnowledge`, 行91-156):

```java
// 1. Query 扩展
List<String> queries = expandQuery
        ? queryExpander.expand(query)    // 1→4个查询
        : List.of(query);

// 2. 收集各路检索结果
List<List<Map<String, Object>>> allRankings = new ArrayList<>();
for (String q : queries) {
    if (useVector) {
        allRankings.add(vectorStoreService.searchKnowledge(userId, q, topK * 2));
    }
    if (useBm25) {
        allRankings.add(bm25Service.search(userId, q, topK * 2));
    }
}

// 3. 融合（RRF 或 简单合并）
List<Map<String, Object>> fused = (useRrf && allRankings.size() > 1)
        ? rrfFusion(allRankings, topK * 2, rrfK)
        : simpleMerge(allRankings, topK * 2);

// 4. Cross-Encoder 精排
return useRerank
        ? rerankerService.rerank(query, fused)
        : fused.stream().limit(topK).toList();
```

**知识库与笔记分开检索**: 两种数据性质不同，分开检索、分开融合、最后合并时笔记优先。

**检索路径全景**（知识库，topK=5，每路取10）:

```
Q0 ──┬── 向量(10) ── BM25(10)
Q1 ──┬── 向量(10) ── BM25(10)
Q2 ──┬── 向量(10) ── BM25(10)
Q3 ──┬── 向量(10) ── BM25(10)
                      │
                      ▼ 最多80个候选
                RRF 融合去重排序
                      │
                      ▼ ~10个候选
              Reranker 精排 + 动态阈值
                      │
                      ▼ 最终 5 个结果
```

**消融开关**: 每个组件（QueryExpander/VectorSearch/BM25/RRF/Reranker）都可通过 `AblationConfig` 独立开关，用于量化每个组件的贡献（见2.6节）。

| 配置 | Recall@5 | MRR | 相对提升 |

### 3.1 四维LLM评估指标

**文件**: `evaluation/service/EvaluationService.java`

4个指标全部使用 LLM-as-a-Judge 模式，`temperature=0` 评估专用模型保证确定性输出。4个评估调用通过 `CompletableFuture.supplyAsync` 并行执行，120s超时保护。

#### Faithfulness（忠实度）

**评估对象**: 生成器（回答是否基于检索文档，有无幻觉）

**评估方式** (`EvaluationService.java:143-250`):

```
Prompt → LLM 将回答拆为原子声明 → 逐条判断 SUPPORTED/NOT_SUPPORTED
Faithfulness = SUPPORTED数量 / 总声明数量
```

**多层降级解析** (行193-225):
- 第1层：精确正则匹配 `CLAIMS:` 和 `FAITHFULNESS_SCORE:`，逐行解析 `SUPPORTED/NOT_SUPPORTED`
- 第2层：宽松正则匹配 `SUPPORTED` / `NOT_SUPPORTED` 关键词（兼容格式偏差）
- 第3层：只提取 `FAITHFULNESS_SCORE: 0.XX` 数值
- 第4层：整体打分降级（0-10分 → 归一化）

#### Answer Relevancy（答案相关性）

**评估对象**: 生成器（回答是否直接回应了用户问题）

**评估方式** (`EvaluationService.java:254-332`):

```
Prompt → LLM 根据回答反向推导出3个可能的问题
       → 计算每个推导问题与原始问题的语义相似度(0-1)
Answer Relevancy = 3个相似度的平均值
```

**设计要点**: 使用 LLM 自评相似度，不混合 Embedding 相似度。Embedding 模型对中文语义相似度计算质量参差不齐，混合后可能引入噪声。

#### Context Precision（上下文精确度）

**评估对象**: 检索器（检索到的文档中有多少是真正相关的，排序是否合理）

**评估方式** (`EvaluationService.java:336-449`):

```
Prompt → LLM 顺序判断每个上下文 RELEVANT/NOT_RELEVANT
       → 位置加权计算 Precision@k

Precision@k = 前k个文档中相关文档的比例
最终分数 = Σ(Precision@k × rel(k)) / 总相关文档数
```

**位置加权公式** (`computePositionWeightedPrecision`, 行404-427):

```java
int relevantCount = 0;
double precisionSum = 0.0;
for (int k = 0; k < total; k++) {
    if (relevances[k]) {
        relevantCount++;
        precisionSum += (double) relevantCount / (k + 1);  // Precision@k
    }
}
return relevantCount > 0 ? precisionSum / relevantCount : 0.0;
```

排名靠前的相关文档贡献更大的权重，排名靠后的相关文档贡献较小的权重。这符合 RAG 场景：用户主要看前几条结果。

#### Context Recall（上下文召回率）

**评估对象**: 检索器（检索是否遗漏了关键信息）

**限制**: **仅回归测试使用**。生产环境没有 Ground Truth（标准答案），无法评估召回率。

**评估方式** (`EvaluationService.java:453-512`):

```
前置条件：RagTrace.groundTruth 不为空

Prompt → LLM 将标准答案拆为独立句子
       → 逐句判断检索上下文是否包含支撑信息 (SUPPORTED/NOT_SUPPORTED)
Context Recall = SUPPORTED句子数 / 总句子数
```

无 Ground Truth 时返回 `-1.0`，综合评分自动跳过此指标。

#### 四指标并行执行

```java
// EvaluationService.java:75-84
CompletableFuture<Double> faithfulnessFuture = hasDocs
        ? CompletableFuture.supplyAsync(() -> evaluateFaithfulness(trace), taskExecutor)
        : CompletableFuture.completedFuture(0.0);
CompletableFuture<Double> relevancyFuture = CompletableFuture.supplyAsync(
        () -> evaluateAnswerRelevancy(trace), taskExecutor);
CompletableFuture<Double> precisionFuture = hasDocs
        ? CompletableFuture.supplyAsync(() -> evaluateContextPrecision(trace), taskExecutor)
        : CompletableFuture.completedFuture(0.0);
CompletableFuture<Double> recallFuture = hasGroundTruth
        ? CompletableFuture.supplyAsync(() -> evaluateContextRecall(trace), taskExecutor)
        : CompletableFuture.completedFuture(-1.0);
```

4个LLM调用并行执行，总耗时从串行12秒降为并行1-3秒。使用自定义线程池 `taskExecutor` 而非 `ForkJoinPool.commonPool()`。

### 3.3 综合评分与自动诊断

**简历对应**: 实现**故障诊断**。

#### 综合评分公式 (`EvaluationService.java:105-133`)

**生产环境**（无 Ground Truth，三指标 + 规则）:

```
LLM评估分 = Faithfulness×0.4 + AnswerRelevancy×0.35 + ContextPrecision×0.25
          （权重归一化: 0.4+0.35+0.25=1.0）

规则评估分 = (100 - 各项扣分) / 100

综合分 = harmonicMean(LLM评估分, 规则评估分)
```

**回归测试**（有 Ground Truth，四指标 + 规则）:

```
LLM评估分 = Faithfulness×0.3 + AnswerRelevancy×0.3
          + ContextPrecision×0.2 + ContextRecall×0.2

综合分 = harmonicMean(LLM评估分, 规则评估分)
```

**为什么用调和平均**: 对低分更敏感。LLM评估0.9 + 规则评估0.3 → 调和平均0.45（加权平均是0.6），任何一个维度有明显缺陷都会被拉低。

**评级标准**:

| 评级 | 综合分 |
|------|--------|
| 优秀 | ≥ 90 |
| 良好 | ≥ 75 |
| 及格 | ≥ 60 |
| 不及格 | < 60 |

#### 自动诊断 (`EvaluationService.java:542-566`)

根据四指标组合反推问题根因：

| 诊断条件 | 诊断结论 | 优化建议 |
|---------|---------|---------|
| Context Precision < 0.6 且 Context Recall < 0.6 | 检索精度和召回都低 | 优化Embedding模型、Chunk切分或召回策略 |
| Context Precision < 0.6 且 Context Recall ≥ 0.6 | 检索到了不相关的文档 | 优化Reranker或TopK |
| Context Recall < 0.6 且 Context Precision ≥ 0.6 | 遗漏了关键文档 | 优化Query扩展或降低TopK阈值 |
| Faithfulness < 0.6 | 忠实度低，模型存在幻觉 | 优化Prompt约束或更换模型 |
| Answer Relevancy < 0.6 且 Faithfulness ≥ 0.6 | 答非所问但回答本身忠实 | 检索文档不对，检查检索链路 |
| 规则评估耗时 > 10s | 响应过慢 | 检查LLM API延迟、ChromaDB连接、BM25索引大小 |

## 四、质量闭环

**简历对应**: 实现**质量闭环**。

```
用户提问
    │
    ▼
RAG 检索 + 生成 ──→ RagTrace（全链路数据记录）
    │                    │
    ▼                    ▼
用户收到回答          每日02:00自动采样评估
    │                    │
    ▼                    ▼
用户反馈(1-5分)      EvaluationReport
    │                    │
    │   ┌────────────────┘
    ▼   ▼
  评估优先级调度:
  ├─ 低分反馈 → 必须评估
  ├─ 规则异常 → 必须评估
  └─ 其他 → 采样评估
    │
    ▼
  综合评分 + 评级 + 自动诊断
    │
    ├─→ 周报趋势分析（每周一）
    ├─→ 低分告警
    └─→ 诊断建议 → 指导优化
           │
           ▼
  消融实验验证优化效果 (BASELINE vs R-1~R-5)
           │
           ▼
  回归测试确认无退化 (POST /evaluation/regression)
           │
           ▼
  下次迭代...
```

**闭环的四个环节**:

1. **数据采集**: 每次RAG调用自动生成 `RagTrace`，记录 question/answer/retrievedDocs/latency/tokenUsage；用户可提交1-5分反馈
2. **自动评估**: 每日凌晨采样评估 + 每周周报；低分反馈和异常Trace 100%评估，正常Trace按比例采样
3. **诊断定位**: 四指标组合 + 规则评估 → 自动诊断 → 精确定位问题（幻觉/答非所问/检索遗漏/排序噪音/响应过慢）
4. **验证优化**: 消融实验量化各组件贡献 → 回归测试确认优化不引入退化 → 参数实验( TopK/RRF_K )找到最优配置

### 从80条候选到8条最终结果的筛选链路回顾

```
80条原始候选(8路×10条)
    │
    │ RRF: 多路共识加权，不同query和不同检索方式的排名交叉验证
    │ 同一chunk在多路中重复出现 → RRF累加分高
    │ 无关chunk只在少数路径出现且排名低 → 自然淘汰
    ▼
10条 RRF候选
    │
    │ Rerank: Cross-Encoder 逐条精判语义相关性
    │ 纠正了A4的排名(从RRF第6提升到Rerank第3)
    │ 纠正了C1的排名(从RRF第9降到Rerank 0.41)
    ▼
8条 Rerank候选 (动态阈值过滤掉 C1 和 E1)
    │
    │ 最终截断 topK=5 (用于送给LLM的知识库文档)
    ▼
5条最终文档 → 送给LLM生成回答
```

**每个阶段淘汰了什么**:

| 阶段 | 输入 | 输出 | 淘汰原因 |
|------|------|------|---------|
| 向量+BM25检索 | 知识库全部chunk | 80条 | 语义匹配和关键词匹配的初步筛选 |
| RRF融合 | 80条 | 10条 | 多路共识：出现路数少、排名低 → 分数低 → 淘汰 |
| Rerank精排 | 10条 | 8条 | Cross-Encoder深度语义判断：C1(运动)不够直接、E1(机器学习)完全无关 |
| 动态阈值 | 8条 | 8条(最终) | B4和A2虽边缘但有用，保留作为上下文补充 |


## 附录B：各环节兜底策略

| 环节 | 可能故障 | 兜底方案 |
|------|---------|---------|
| Query 扩展 | LLM API 超时/限流 | 仅使用原始查询，不阻断 |
| 向量检索 | ChromaDB 连接失败 | 降级为 MySQL 余弦相似度扫描 |
| BM25 检索 | Lucene 异常 | 返回空列表，不阻断流程 |
| RRF 融合 | 仅一路检索结果 | 跳过融合，直接返回 |
| Rerank 精排 | API 调用失败 | 返回原始排序结果 |
| Faithfulness 评估 | 声明拆分解析失败 | 4层降级解析 → 整体打分 |
| Answer Relevancy 评估 | 反向生成解析失败 | 降级为整体打分 |
| Context Precision 评估 | 位置加权解析失败 | 降级为整体打分 |
| Context Recall 评估 | 无 Ground Truth | 返回 -1.0，综合评分跳过 |
| 任何单次 LLM 评估调用 | 120s 超时 | 返回默认值 0.5 |
| 整个检索 | 没搜到任何文档 | 返回"未找到相关文档" |
